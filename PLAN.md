# MapNC build plan

Static, client-side proof of concept. No backend, no build step. Everything runs in the browser.

## Files

| File | Role |
|------|------|
| `index.html` | Page shell, controls, script tags |
| `css/style.css` | Layout |
| `js/geo.js` | Pure geometry: ground size, US detection, source choice, Terrarium zoom/tile maths, size cap (no DOM, unit-testable in Node) |
| `js/app.js` | Leaflet map, rectangle drawing/editing, status panel |
| `js/sources.js` | 3DEP + Terrarium fetchers, stitching, resampling to a ground-correct grid |
| `js/heightmap.js` | Elevation → grey mapping, 16/8-bit PNG encoding (own encoder + `CompressionStream`) |
| `js/track.js` | GPX (TCX/FIT if easy) parsing, route overlay, transparent route PNG |
| `vendor/` | Leaflet 1.9.4 (vendored, so no CDN dependency) |

## Phases

1. **Map + region selection** *(done)*: Leaflet map, draw/resize a rectangle, ground-size and output-grid estimate, size cap, source auto-detect and resolution readout.
2. **Elevation fetch + stitch** *(done; tested with real Terrarium data and a mocked 3DEP service)*: Terrarium tiles → decode; 3DEP `exportImage` (float32 GeoTIFF via geotiff.js), split into sub-requests; resample to an equirectangular grid corrected by cos(lat) so aspect is ground-true.
3. **Heightmap + export** *(done; PNG encoder verified bit-exact with Pillow, `js/heightmap.js` uses the browser's CompressionStream instead of UPNG.js, so no dependency)*: auto / manual range, height curve (gamma; replaced the linear vertical exaggeration, which CAM software does better), 8-bit canvas preview, 16-bit PNG from `Uint16Array`, optional 8-bit, elevation range and metres per grey level.
4. **Track overlay** *(done; TCX supported, FIT not; the route was once burned into the heightmap, now removed in favour of separate PNG/SVG/DXF layer exports)*: GPX parse, fit region to track bbox + margin, draw route over the preview, export transparent route PNG.
5. **README + Pages deploy** *(README and workflow written; Pages source must be set to GitHub Actions once in repo Settings)*, attributions (USGS 3DEP, AWS Terrain Tiles and its underlying datasets, map tile provider).

## Decisions and open risks

- **Carve sizes** (owner, 2026-10-02): 3×3 in up to 16×16 in. At 4096 px that is about 0.02–0.1 mm per pixel, far finer than a bit's stepover, so the cap is rarely the limit; source resolution is. Size/resolution/file-size limits to be refined later.
- **Cap**: native grid at most 4096 px per side and 16.7 M samples total (Float32 = 64 MB). Over the cap, the rectangle turns red and export is blocked. Phase 2 may offer coarser resampling instead.
- **Aspect**: Mercator is locally conformal, but scale varies with latitude across the box. The output grid is built from ground distance (`Δlon · cos(midLat)` by `Δlat`), not from raw tile pixels.
- **Auto-detect**: 3DEP only when the whole rectangle lies inside rough CONUS or Hawaii bounds. Alaska coverage is patchy, so it falls back to Terrarium unless the user forces 3DEP. Rough boxes include some ocean and Canada/Mexico; the ImageServer returns NoData there, which phase 2 must handle.
- **CORS** (2026-10-02): AWS Terrarium returns `Access-Control-Allow-Origin: *`. 3DEP: the dev sandbox blocks `elevation.nationalmap.gov`; the project owner confirmed from a browser that it works. Requests are split into chunks of at most 2000 px per side. **Checked against the real 3DEP service (2026-10-02)**: a float32 TIFF comes back with `Access-Control-Allow-Origin: *`; requests of 2000 x 2000 px work (about 16 MB, 4-5 s), but 3000 x 3000 and 4000 x 2000 fail with HTTP 500 after ~20 s even though the service JSON advertises `maxImageWidth/Height` of 8000, so the 2000 px chunk stays and the JSON limits are NOT trusted. Eight parallel 2000 px requests succeeded. The full app flow (sample route, auto load, 1410 x 2048 px 16-bit export, ~11 s) works. Requests finer than 10 m are served from finer source data where it exists (1.7 m and 1 m requests over the Sierra Buttes returned lidar-like detail), so the "10 m native" figure used for the scale factor is a lower bound there. Requests and tiles are retried twice on a network error or HTTP 5xx. Cross-check against Terrarium over the same box: correlation 0.92 at 10 m cells, no sign of a georeference offset (the best shift barely improves the match); Terrarium is smoother on steep ground.
- **Cap**: adjustable in Advanced (2048 to 16384 px per side). 16384 needs roughly 1.5 GB for a Terrarium fetch and may crash the tab.
- **Terrarium resolution** is a tile-pixel size. Underlying data is far coarser in many places (about 30 m globally), so the UI shows tile pixel size and says so.
- **Map tiles**: OpenStreetMap standard tiles are fine for a low-traffic PoC but not for heavy use (tile usage policy). Swap the provider before wider sharing.
- **Output resolution** (owner feedback, 2026-10-02): a 2.4 × 3 km region at 10 m is only ~240 × 300 px, which looks jagged in Vectric / Carbide Create, especially the route. Output size is now independent of source resolution (Auto = at least 2048 px long side; scale; long-side pixels; metres per pixel). Upscaling is cubic (Catmull-Rom for Terrarium, `RSP_CubicConvolution` for 3DEP), and the route is rasterized at output resolution. The "native" resolution used for the scale factor is 10 m for 3DEP and 30 m for Terrarium. 3DEP may serve its higher-resolution lidar DEMs when asked for finer pixels; this has not been checked against the real service.
- **Route layer at very high resolution** (done, 2026-10-02): PNG compresses blank areas ~1000:1, so file size was never the limit; memory was. The route layer is now drawn and compressed a band of rows at a time (`createBandRasterizer` + `encodePngStream`), verified identical to the whole-image path. An 11281 × 16384 layer (705 MB raw) took ~9.5 s, added ~33 MB of memory in Node and produced a ~1.1 MB file. Capped at 16384 px on the long side because the program opening it must hold the whole bitmap (and wide lines make drawing slow). The route is also exported as SVG/DXF (`js/vector.js`), checked with ezdxf's auditor.
- **Sidebar and loading** (owner feedback, 2026-10-02): the sidebar became collapsible panes plus an always-visible data strip. The separate "Fetch" step is gone: elevation loads automatically 700 ms after the region/resolution/source stops changing, is cancelled by any change, and never runs mid-drag. Outputs over ~4.2 M samples wait for a click (a download of tens of MB per tweak is not acceptable). The elevation source moved under Advanced. Fetch-on-export was rejected because the live preview (grooves, range, clipping) needs the data.
- **Route clean-up** (owner idea, 2026-10-02): geometric only, no timestamps needed. Order: spike removal, minimum spacing, Gaussian smoothing along arc length (resampled evenly so density does not bias it; ends fixed), Ramer-Douglas-Peucker simplification. Spike detection ignores tracks sampled more sparsely than the threshold (a real turnaround is indistinguishable from a spike there). Checked against a synthetic path with known ground truth. Not yet tried on a real noisy tracker file beyond the sample plus injected noise.
- **Manual route editing** (owner request, 2026-10-02): pipeline is original -> automatic clean-up -> manual edits. Edits live in the editing view of the sidebar (a separate view rather than inline panes, per owner feedback). Clean-up settings lock while edits exist, because changing them would silently discard hand work; Discard unlocks. Undo is a stack of compact typed-array snapshots (100 deep). Handles use pointer events with pointer capture and the app's own hit-testing (touch radius larger than mouse); a second pointer is ignored mid-drag and pointercancel ends the gesture. Handles are limited to 1500 in view. Shift+drag needed a patch to Leaflet's Draggable (vendored at a fixed version) and box-zoom turned off. The heightmap recomputes on drop, not on every pixel of a drag. Not yet tried on real touch hardware (synthetic pointer events only).

- **Lake flattening** (done, 2026-10-02, `js/lakes.js`): optional, from the OSM lake outlines. Flat water only, no carved depth. Level per lake is the median of the DEM inside its outline, never a global level (lakes in one region differ by hundreds of metres). Islands (inner rings of a relation) stay dry because rings of one relation are filled together with the even-odd rule. Skipped: lakes whose samples already span under 5 cm, lakes under 4 pixels, rivers mapped as areas (`water=river|stream|canal|ditch|drain...`), and any lake with an incomplete outline (filling a half-closed ring or missing an island is worse than leaving it). No-data inside a lake takes the lake's level. The change is applied in place with an undo patch (index plus old value per changed sample), so unticking restores the original samples with no refetch and no second copy of the grid. Case study before building (Sierra Buttes sample): the big lakes are already hydro-flattened in 3DEP (SD 0.00 m), only small ponds and wet meadows are noisy (0.3 to 0.7 m), so the gain on 3DEP is small; on Terrarium (z13, about 15 m/px) the big lakes are nearly flat too (SD 0.04 to 0.15 m) and sit 6 to 7 m above 3DEP (different datum and vintage), small ponds are noisier (SD 1.3 to 2.9 m). Tested with mocked Overpass only. Because the heightmap now depends on OSM data, the ODbL credit applies to what is carved from it, and the PNG records `LakesFlattened`.
- **Streaming heightmap export** (done, 2026-10-02): the main PNG is now encoded a band of rows at a time (`encodeGreyStream`, built on `encodePngStream`, which gained 16-bit support), with progress. Same pixels and metadata as the whole-image encoder (tested byte for byte after inflating, for 8 and 16 bit). A 12000 x 12000 16-bit export added about 77 MB of memory in Node, where the whole-image encoder needs 275 MB for its uncompressed copy alone. This does not by itself raise the size cap: the preview canvas is still full size (see BACKLOG).

## Ocean plan (sea level and bathymetry)

Status: plan only, nothing built. Written 2026-10-02.

**What the data does today.** 3DEP returns NoData over open water, so the sea reaches the heightmap as magenta in the preview and grey 0 in the export. That looks like deep water by accident, and it is the lowest value, so the land keeps the whole grey window. Terrarium already includes GEBCO bathymetry, but at about 450 m at best, so a coast looks smooth and jagged at once.

**A bathymetry source that works (checked 2026-10-02).** NOAA NCEI's global topo-bathy mosaic, `gis.ngdc.noaa.gov/arcgis/rest/services/DEM_mosaics/DEM_global_mosaic/ImageServer`. It is the same ArcGIS `exportImage` API as 3DEP. A float32 TIFF comes back with `Access-Control-Allow-Origin: *`. The service pixel size is 1/9 arc-second (about 3.4 m) where the coastal models exist, coarser elsewhere, and the values run from -9982 m to +6180 m across the globe. Spot checks: Monterey Bay gave -1185 m over the canyon, -100 m on the shelf, +82 m inland; off Oahu -19 m near the shore to -1700 m offshore. A 2000 x 1333 px request over Oahu returned 11.5 MB in 3.3 s, and the service advertises 20000 px per side (the 3DEP lesson says not to trust that, so keep 2000 px chunks and test larger ones). Land and sea are in one raster, so no seam logic is needed when it is used alone. Vertical datums differ by about a metre near the shore.

**Two separate features, because they answer different questions.**

1. **Flat sea.** Everything that is sea becomes one flat level (0 m by default, editable). "Sea" is found by a flood fill from the border: start from border samples that are at or below the level (or no-data), and spread through connected samples at or below it. A low land basin that touches the border (Death Valley at -86 m, the Salton Sea, a polder) would be filled wrongly, so this is an unticked option, with the clamped percentage shown and a warning when over half the region is flooded. Needs no new data. For 3DEP, no-data connected to the border counts as sea.
2. **Bathymetry** (carved sea floor, for islands). The sea floor below the waterline is kept, but it cannot share the land's grey range (a 1200 m trench would flatten a 300 m island). So the grey mapping gets a **sea band**: land from the waterline up keeps the linear mapping into the upper part of the range, and depth below the waterline is compressed into a bottom band (a slider for its share, default about 15%), with a depth cap (default 100 m, beyond which the floor is flat) or a curve (log-like) so the shelf has detail. Monotonic, so the CAM sees a smooth surface. The PNG records the sea band, like the existing curve text.

**Data flow for bathymetry.** The region is detected as coastal when 3DEP returns no-data connected to the border, or when Terrarium shows samples below 0. For a coastal 3DEP region, fetch the NOAA mosaic on the same grid and merge: keep 3DEP wherever it has data (finer on land), take NOAA wherever 3DEP is no-data or below the waterline, and blend over a few pixels at the seam. Outside the US, use Terrarium as it is (it already carries GEBCO). A source option, "Sea floor from: NOAA / Terrarium / none", under Advanced.

**Pieces, in order.**
1. Flat sea: flood fill and the option, with an undo patch like the lakes (cheap, no new data, solves the island case at once).
2. Sea band in `toGrey`: `opts.sea = { level, depthCap, band }`, tested for monotonic and continuous at the waterline, with the preview and histogram reading it.
3. NOAA fetch and merge for coastal 3DEP regions (reuses `fetch3dep` chunking and `parseDepTiff`; a new source id and credit line for NOAA NCEI).
4. Touches: 3D view gets an optional sea plane at the waterline; contours below the waterline use negative levels and are checked; a coastline layer (the zero contour) in the SVG/DXF.

**Tests to write.** A synthetic island (a cone with no-data sea, then with real depth below 0): flat sea, border flood fill, the enclosed-basin guard, sea band monotonic; a mocked NOAA service for the merge and the seam; a region with no sea must come out unchanged.

**Open questions for the owner.**
- On a heightmap with bathymetry, should the sea floor be carved as relief (deeper = lower, as above), or only the waterline (flat sea)? Both are planned; the question is which one to build first.
- A depth cap of about 100 m is a guess. For a typical island carve, how deep do you want the floor to read?
- Is the waterline always 0 m, or do you want it editable (tide, lake level)?

## Decisions: elevation fixes and edge border (2026-10-03)

- **Fixes are edits with undo, applied in a fixed order.** Fill gaps, flatten lakes and raise floor all edit `elevation.data` in place and keep patches (`js/fixes.js`, `js/lakes.js`). Any change reverts every patch and reapplies the ticked ones as gaps, then lakes, then floor, so the result does not depend on tick order. The lake outlines are cached, so re-running is cheap.
- **Gap filling.** Gaps are 8-connected runs of NaN. Each pixel takes a blend, weighted 1/distance, of the nearest samples left, right, up and down, read from the original data only (order-independent; exact for a plane). Gaps over 2% of the grid are left alone and reported, because they are normally outside the source's coverage or open sea.
- **Floor.** "Raise everything below X m" changes the data, not just the window, so the automatic range, the 3D view, contours and the STL all agree. It is the plain flat sea for the ocean plan (the flood fill is the careful version).
- **Edge border lives in `toGrey`, not in the elevation.** It works on the final grey value (after range, exaggeration and curve, before invert), so "top" and "bottom" mean the top and bottom of the window whatever the settings. Styles: rim (flat band), chamfer (linear), rounded (quarter circle: tangent to the terrain, steep at the edge). Distance is to the nearest edge (mitred corners). Width is in millimetres of the carve, converted with the carve size, so it needs that; with no carve size the border is off and says why. It is in the PNG, the STL and the preview, not the 3D view. The route layers and contours do not move.
- **Canada source (built, 2026-10-03).** NRCan's High Resolution DEM mosaic through its WCS 1.1.1 endpoint (`datacube.services.geo.ca/wrapper/ogc/elevation-hrdem-mosaic`; the `mrdem` and `cdem` names on the same host only redirect to it). It shares the chunked fetch with 3DEP (`fetchGridded` in `js/sources.js`): request pixels square in degrees, resample from the extent the GeoTIFF reports. Checked live: values for Ottawa and the placement of overlapping requests (a one-pixel shift always matched worse than none). Three findings drove the design.
  - Coverage is patchy: a remote part of north-western Ontario came back 87% no-data. So Auto only keeps the Canadian result when it is under 2% no-data, otherwise it falls back to Terrarium with a note. Choosing it by hand keeps whatever it has.
  - The pixel size is not stated, so it is assumed to be 10 m (1 to 2 m in lidar areas, 20 to 30 m elsewhere).
  - Auto's "inside Canada" test is a coarse outline with all four corners required inside (`CANADA_OUTLINE` in `js/geo.js`); a region that crosses the border or a coast gets the global source, since 3DEP would be empty on the Canadian side. The `interpolation` parameter is ignored by the service (identical output for any value), so none is sent.

## Decisions: tiling (2026-10-03)

- **A tile is a window of the one finished grid.** `js/tiles.js` plans the cut from the carve size, a largest piece and an overlap; the export reads each tile straight from `grey.data` (`encodeGreyStream` takes a `view` window, no copy). So every tile shares the grid's pixel size, its elevation window and its edge border, and the border only lands on the outer edges. This is why heights match across seams without any extra work.
- **Equal tiles, evenly spread.** All tiles are the same size (one stock size fits every piece) and run from edge to edge; neighbours overlap by at least the requested amount (more when the division is not exact). The overlap is cut twice from identical data, which is what the machine registers on. Rows and columns count from 1 at the top-left (north-west). The piece limit is one number for both directions.
- **What tiling does not do.** Tiles are cut from a grid that already exists, so they fix a carve that is too big for the machine, not a grid that is too coarse for a typical stepover. For that, the advice now says to raise the size cap or carve a smaller area. Giving each tile its own fetch (or its own cubic resample) at the pixel size the stepover needs would lift the memory cap, but it means re-running fixes, lakes, the border offset and the shared window per tile, and the seams would no longer be guaranteed identical. It is in the backlog, not built.
- **Output.** One ZIP (`js/zip.js`, stored entries, no ZIP64): a 16- or 8-bit PNG per tile (with its place, offset and bounds in the text chunks), optionally a route layer PNG per tile (the same band rasterizer on the tile's sub-bounds; it matches the whole route layer exactly), optionally a DXF per tile (the route, contours and map layers cut at the tile edges by `clipPolyline`, with the tile's own corner marks), and `tiles.txt` with every tile's offsets in mm. The SVG and STL exports and the layered map are not tiled.
